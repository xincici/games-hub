## 玩法与数据

14 张手牌，点一张打出去（进**出牌区**，正面朝上），然后**自动从牌墙摸一张**（新牌先停手牌最右，
再打出一张时整副手牌重新排序）。凑成 **4 组 + 1 将** 或 **七对子** 即胡；牌墙摸完未胡即本局结束。

- **`board.js` 是纯逻辑且不 import 任何东西**（和 24 点同一个理由）：可以直接用 node 跑离线自检
  （`node -e "import('./src/games/solo/board.js')"`）。整副 136 张（`m/s/p` 各 9×4 + 字牌 7×4），
  任何牌在一局里都不会超过 4 张；**每一局都缺一门**（用户要求）—— 三个花色随机去掉一个，
  整局（手牌与牌墙）都不会出现它，字牌照旧；于是整副牌从 136 张变成 **100 张**。
- **每一局都是「可赢」的，但不再是一步之遥**：`newRound()` 先造一副**能胡的 14 张**，从里面拿走
  `SPARES = 2` 张换成不相干的，被拿走的 2 张都埋进牌墙前 `needBy` 张之内。
  `board.js` 还导出 `waits(tiles13)`（13 张听什么）用于自检。
  实测 800 局：**「odds 换回 spares 就成胡」100% 成立、发出来的手牌本身从不是胡牌**
  （撞上会重发，见 `newRoundSafe()`）。
  回归用 `node scripts/check-solo.mjs [局数]`（纯逻辑、不开浏览器）：它同时断言每张牌 ≤ 4 张、
  缺一门比例（必须 100%）、spares 一定在牌墙里且不深于本档 `needBy`、胡牌判断的正例与反例、以及排序。
  **难度实测**（同一个贪心策略「每一手都挑打完听牌数最多的那张」，每档 300 局）：
  连胜 0 → **胜率 29.3%**、5 → 33.3%、12 → **25.7%**。乱打则会把听牌打没，最后摸完牌墙判负。
- 牌墙最多 **40 张**（`WALL_SIZE`）：牌堆 10 列 × 4 层，**每一张都画得出来**（用户要求「按真实数量
  呈现」，数量从 20 → 30 → 40 提了两次）。
- **起手不再「只差一步」**（用户要求「初始的牌别那么整齐」）：`SPARES = 2` —— 先造一副能胡的 14 张，
  从里面**拿走 2 张**（`spares`），各换一张池子里「不相干」的（`odds`）。所以起手是**离胡牌两步**，
  玩家要把这两张多余的依次打掉，而被拿走的 2 张都埋在牌墙前 `needBy` 张之内等着摸回来。
  保证形式也相应升级（不再是「打掉 odd 就听 need」）：**把 odds 换回 spares，正好是一副能胡的牌**，
  自检对每档都断言这条 + 两张 spare 都在牌墙内且不深于 `needBy`。实测 800 局 100% 成立。
- **难度随当前连胜温和递增**（用户要求「适当的控制连胜的难度递增」）：`roundPlan(streak)` 给两个旋钮 ——
  **牌墙张数**（可摸的机会）与 **need 埋多深**（几手才能摸到），连胜 12 之后封顶不再加难：
  | 连胜 | 牌墙 | spares 埋在前几张 |
  | --- | --- | --- |
  | 0~1 | 40 | 8 |
  | 2~3 | 36 | 10 |
  | 4~6 | 32 | 12 |
  | 7~9 | 28 | 15 |
  | ≥10 | 24 | 18 |
  实测（每档 25 局）：牌墙均值 40 → 36 → 32 → 28 → 24，spares 位置均值随 `needBy` 变深。
  **任何一档都仍然保证「odds 换回 spares 就成胡」**（自检逐档断言）。
- **「新游戏」= 从头开始，且当前连胜 > 0 时先二次确认**（与 24 点一致）：确认后**当前连胜清零**
  （最长连胜作为记录保留）、按 `streak = 0` 发一局新的。想保留连胜继续打，就用浮层上的「再来一局」。
- 胡牌判断 `isWin(tiles, kongs = 0)`：**手牌张数 + 3 × 杠数 必须等于 14**，再拆 `4 − 杠数` 组 + 1 将
  （七对子只在没有杠时成立）；拆组用「从最小的牌开始拆」的贪心（刻子 or 顺子；字牌不能连）。
  `waits(tiles13, kongs)` 同理（要求 `13 + 3 × 杠数`）。**离线自检里有正例与反例**，改判断逻辑先跑它。
- **杠牌**（用户要求）：手里凑齐 **4 张一样**的牌时 ——
  - `displayItems` 把这 4 张从原位置**抽出来合成一个杠组**（`.kong-group`，橙色框住），
    **框必须用 `outline` 画、组上不能有 `padding`**：一行正好是「7 张牌 + 6 个间隙」顶满容器，
    多 2px padding ×2 就会把后面的牌挤到下一行（用户报的「边框把牌挤换行了」）；
    outline 不占布局空间，配 `outline-offset: 2px` 视觉上一样贴在四张牌外面。
    **但真正让它不换行的是手牌区改成了 grid**（见「布局与界面」里手牌区那条 ⚠️）——
    只去掉 padding 治不了「杠组位置不同就换行」。
    所以"刚摸到第 4 张"也能立刻成组（抽牌时不要求相邻，靠 `tileKey` 找齐）。
    ⚠️ **成组 ≠ 立刻画框**：`framing` 走 `canFrame = !dealing && !flying` ——
    摸牌是「先提交、再让替身飞」，只判 `!dealing` 的话，第 4 张还在空中、它就已经被抽成杠组并画上橙框了
    （用户报的「牌没入位之前框已经展示了」）。tooltip 的 `v-if` 同样用 `canFrame`。
    实测时序：`t=397ms` 飞行中「已成组、未画框、无 tooltip」→ `t=811ms` 落位后「画框 + 出 tooltip」；
    **「替身在飞却已经画框」的帧数为 0**（tooltip 也是 0）；落位后手牌 14 张、行槽位 `[7, 7]`。
  - 组上方浮出 **tooltip** `.kong-tip`（文案就是「杠牌」，**不带 emoji**），点它就杠；不想杠就照常点牌打出去，
    4 张少了任何一张 tooltip 自然消失（`watch(kongOpts)` 负责开关）。
    **热区**：按钮本身 `padding: 9px 18px` + `font-size: 14px`（实测 **64×38**），再用 `::before`
    往**上 12px / 左右 12px** 各扩一圈 —— **绝不往手牌那侧扩**（那会让「想点牌」误触发杠牌）；
    实测中心、上 8/11px、左/右 10px 都命中 tooltip，超出 12px 才落到别处。朝手牌那侧的
    `::after` 小三角设了 `pointer-events: none`（它是唯一伸向牌面的部分）。
    ⚠️ **绝对不能用 `transform` 居中**：`App.vue` 有全局规则
    `#app button:not(:disabled):active { transform: translateY(1px) }`，按下的瞬间会把
    `translateX(-50%)` 顶掉 → tooltip 横跳半个宽度、指针跟丢、`:active` 结束又跳回来 ——
    用户报的「点 tooltip 会出现晃动点不到」就是这个。改用**独立属性 `translate: -50% 0`**
    （与 `transform` 是两个属性、会叠加，全局那条覆盖不到它；`.flying` 也是这个写法）。
    实测：按下时**横向位移 0**、纵向 1px（就是全局的下沉反馈 ✓）、指针仍命中 tooltip；
    松开后确实杠成功（手牌 14 → 11、杠组 1、杠行 4 张、牌墙补摸 1 张）。
    （注：手牌改成显式槽位后杠组总在行首，`kongTipBelow` 实际恒为 false、气泡总在上方；
    `.below` 那套保留着，布局若变仍然正确。）
  - **tooltip 会按杠组在第几排自动翻向**（用户要求，避免挡住另一排的牌造成误操作）：
    `measureTipSide()` 比较杠组中心与手牌卡片的中线，在下排就加 `.below` 类 → 气泡翻到**下方**、
    小三角朝上；上排仍在**上方**。手牌一变（`watch(displayItems)`）与量宽度后都会重量一次。
    实测：上排时 tooltip 470–498、组 504–562（在上方）；下排时 tooltip 627–655、组 563–621（在下方），
    两种情况都不会压到任何手牌；
  - 杠出去的 4 张进**出牌区最下面一行**的 `.kong-row`（正面朝上、一组一个框、右对齐），再从牌墙**补摸一张**
    （`doKong()` 复用 `drawOne()`）。
    **动画必须是「4 张一起飞」**（用户要求）：第一版只让 `four[0]` 一张飞过去，落位后杠行才渲染出 4 张，
    看起来就是「一张牌出去、落下变四张」。现在飞行替身本身就是一个**含 4 张的 flex 容器**
    （模板里 `flying.tiles` 走 `.flying-kong` 分支，容器尺寸与组内间距都写出发时的实测像素值），
    `flyGroup()` 从头到尾只移动/缩放这一个容器：出发口径 = 手牌里那个 `.kong-group`
    （`groupShape()` 量外层矩形 + 组内单张尺寸 + 组内间距），落点 = 杠行新加的那一组
    （`hiddenKongIndex` 先把它藏起来，再提交 —— 和摸牌/出牌同一套 FLIP）。
    缩放比用**单张牌高**算（`目标牌高 / 出发牌高`），两端的牌看起来一样大。
    实测：飞行组内 **4** 个元素、宽度 `183 → 170 → … → 83 → 82` 单调收缩、高度 `54 → … → 24`、
    飞行期间杠行那一组隐形数为 **1**，落位后手牌 11、杠行 1 组 4 张且可见、无残留隐藏元素。
  - 因为杠完补摸，手牌会变成 11 张 —— **等效张数仍 = 手牌 + 3 × 杠数 = 14**，实测杠后打一张循环正常。
    胡牌的判断统一走 `isWin(hand, kongs.length)`。存档里多一个 `kongs` 字段。
- 胡牌判断（不带杠时）与七对子的细节见上；**校验过 11 张 + 1 杠判胡、14 张带 1 杠不判胡**。
- **失败只记录「这一局」，由玩家自己决定什么时候开新局**（用户要求）：`lose()` 把 `phase` 置为 `lost`
  并**存进存档** —— 退出重进还是这个失败局面（浮层上只有「再来一局」），**不自动开新局**。
  **不统计累计失败**（用户明确不要这个块）。分数区仍是**三格**：最长连胜 / 当前连胜 / 剩余牌数。
- 摸完牌墙 → 本局结束、**当前连胜归零**（最长连胜保留）；胡了 → 连胜 +1、撒花、浮层。
  **最后一张摸完没胡就立刻判负**（用户要求：不用等玩家再打出去）——`drawOne()` 里判胡失败后若牌墙已空，
  等 350ms 直接 `lose()`。
- **胜负遮罩配色照其它游戏来**：`background: var(--mask-color)`、`color: var(--win-color)`，
  输的时候挂 `.lose` 用 `--lose-color`（别自己写黑底白字，主题切换后会和别的游戏不一致）。

## 布局与界面

五块从上到下：**分数区（最长连胜 / 当前连胜 / 剩余牌数，3 格） → 按钮区（左侧「本局没有X」+ 新游戏）
→ 牌墙 → 出牌区 → 手牌区**。牌墙、出牌区、手牌区都在 `.game-area` 里（浮层的定位上下文）。
实测 375×667 各块高 **88 / 72 / 72 / 128 / 129**（牌堆 72、出牌区 4 行、手牌两行），内容总高 **641** < 667；
375×667 与 390×844 纵向/横向滚动都是 **0**；手牌单张 42×54（390 下 44×56）。

- 操作区照 Emoji 下坠那套：`opt-half（文案，flex 3）` + `divider` + `start-wrapper（按钮，flex 3.5）`，
  **按钮自然宽度、不拉伸**。左侧那格显示**本局缺哪个花色**（`omitText`，例如「本局没有万子」，
  没缺就空着）—— 原来这里是「恭喜发财」，用户要求删掉、把缺门说明从牌堆下方挪过来。
- **`.card` / `.divider` / `.game-icon` 的外观都必须在本游戏的 scoped 块里各写一遍**：全局只有
  `--card-*` / `--primary-bg` 这些**变量**，没有这三条规则（每个游戏都自己写，见 point24 等）。
  漏写的症状实测：`.card` 拿到 `background: rgba(0,0,0,0)`、`border-radius: 0`、`padding: 0`
  （分数区/按钮区像裸文本）、`.game-icon` 拿到浏览器默认灰底、`.divider` 是 0×0 全透明
  （统计条上看不到分隔线）—— 用户原话「分数区、按钮区的样式又丢了」。
  另外这三条规则要写在 **`.wrapper` 里面**（`.card` 等元素都是它的后代）✓，并且写完记得
  **`.wrapper` 的闭合括号别丢**：漏掉它 Sass 会报 `expected "}"`，构建直接失败。
- **`.wrapper` 的内边距要写全 `padding: 64px 16px 24px`，不能只写 `padding-top: 64px`**：
  只写 top 会把左右内边距变成 0 → **所有卡片贴到屏幕两边**（用户报的「卡片游戏区都拉伸贴到两边」）。
  左右 16px、底部 24px 与其它游戏一致；容器还要 `box-sizing: border-box` 与
  `color: var(--text-color)`。
- **`--radius-card` 这个变量并不存在**（`App.vue` 只定义 `--radius-tile` 与 `--card-radius`）：
  写 `border-radius: var(--radius-card)` 会解析成空 = **直角** —— 用户报的「胜利遮罩缺少圆角」就是这个。
  遮罩用 `var(--card-radius)`（14px，和卡片一致），实测浮层圆角 14px。
- **`.card` 里绝对不能写 `color: var(--card-color)`**：那个变量是 **`#fff`**（给深色卡片用的），
  浅色主题下就是**白底白字** —— 用户报的「最上方的分数区都没有数字」就是这个
  （实测 `.stat-value` 颜色是 `rgb(255,255,255)`，改掉后是 `rgb(44,62,80)`）。文字颜色统一由
  `.wrapper` 的 `color: var(--text-color)` 给。
- **牌堆**（`.wall-card`）：`.tile-back` 里放的是共享组件 **`shared/MahjongBack.vue`（`fill` 模式）** ——
  **绿色纹理牌背**（`#1f7a4d` 绿底 + 45° 亮纹叠 -45° 暗纹 + 百分比内圈压边），
  与侦探 / 猎手 / 对对碰 / 大师的麻将牌背**同一套纹理**（玩家要求统一；此前这里是自己写的
  「`--primary-bg` 纯色 + 3px/7px 白斜条纹」）。组件自带底色与内圈，`.tile-back` 只留一圈外描边；
  条纹与内圈都用百分比，所以这张 **26×33** 的小牌背上纹理密度与大牌一致（实测四家
  `background-image` 字符串**逐字相同**）。**不带任何图标**
  （用户要求；第一版是绿色渐变 + 内描边 + 🀄 emoji，`background-image` 现在只有
  `repeating-linear-gradient(45deg, rgba(255,255,255,.22) 0 2px, transparent 2px 5px)`），
  **每张剩余牌都画出来**（最多 40 张 = 10 列 × 4 层），用 `position: absolute` 排：牌背 **26×33**、
  列间距 **29px**（26px 牌宽 + 左右各 1px 描边 + **1px 缝** —— 用户要求「适当有一点点间隔」），
  每一层往右错 **2px**、往上错 **4px**（第一版是 5/9，层与层错得太开、看着参差不齐 ——
  用户要求「适当呈现出摞起来的效果即可」），牌背下缘用 `::after` 画 3px 的一圈「厚度」——
  合起来就是「微微摞起来的几层」。实测满堆 **293×44**（4 层共 40 张）、单张 28×35 含描边、相邻牌背间隔 1px。
  牌堆卡片本身 72px（**下面不再有缺门说明**，那行已挪到按钮区左侧）。
  ⚠️ **牌堆卡片必须有 `position: relative; isolation: isolate`**：牌背用内联 `z-index` 排层（0~39，
  每层 10 张），而胜利遮罩是 `z-index: 20` —— 不给牌堆建层叠上下文，第 3 层往上的牌就会画在
  遮罩**上面**（用户报的「第三层牌超出胜利遮罩」）。
  摸走一张就少一张，**牌堆会肉眼可见地变短**（10 张以内宽度跟着缩）。
  （第一版用 `flex` 排、只画 `min(剩余, 12)` 张：看起来是平铺的一条，而且数量永远不变 ——
  用户报的「排列不好看、摸牌后牌堆完全不变」就是这个。）
- **出牌区**（`.discard-card`）：**一共 4 行** ——前三行放打出去的牌（`.discard-row`，
  `flex: 0 0 calc(var(--small-tile-h) * 3 + 4px)` + `overflow-y: auto`，多了才滚动），
  第四行放**杠牌**（`.kong-row`，`justify-content: flex-end` **右对齐**）。卡片高度
  `calc(var(--small-tile-h) * 4 + 32px)`（实测 **128px**）。
  **牌堆涨到 40 张之后，出牌区的牌必须更小才放得下**（用户要求「确保能放下 40 张牌」）：
  `--small-tile-w: 19px; --small-tile-h: 24px`，`.discard-row` 的 `gap` 固定 **2px**（必须与高度
  `3 × 24 + 2 × 2 = 76` 一致，否则会有几像素的内部滚动）。实测 375 一行 15 张 → `[15, 15, 10]`、
  390 → `[16, 16, 8]`，**行内溢出 0**、容量 42 ≥ 40，内容总高 641 / 646，零滚动。
- **手牌区**（`.hand-card`）：14 张、**两行每行 7 张**，尺寸走 `--hand-tile-w`
  = `(100% - 16px - 6 * var(--hand-gap)) / 7`；牌的长宽比固定 1.2824（雪碧图每格 131×168）。
  ⚠️ **必须显式指定槽位（`handSlots` / `slotStyle`），不能靠自动布局**：
  杠组是**一个**元素但占 **4 张牌宽**（`.kong-group { grid-column: span 4 }`）。
  - 用 **flex** 排：换行按「项」算，「4 张 + 杠组」放不下时杠组整体挪到下一行 → 3 行；
  - 用 **grid + 自动布局**：同样不行 —— 杠组落在第 5~7 槽时行尾只剩 3 格装不下 4 格，
    浏览器把它挪到下一行并**在上一行留下空洞**，10 张单牌 + 1 个杠组（共 14 槽）照样摊成 **3 行**。
  （两次都报「有杠的时候换行了」，第二次就是 grid 自动布局 —— 我上一版只把杠组 padding 去掉、
  又**只测了「杠在最前 / 中段」两个位置**，正好都没踩到。）
  现在 `handSlots` 显式排：**第 i 个杠组占第 i 行行首**，其余单牌按显示顺序逐行填空位，
  `slotStyle(i)` 把 `gridRow` / `gridColumn` 写进 style。1 个杠 = 4+3 / 7、2 个杠 = 4+3 / 4+3，
  永远 7+7（3 个杠才需要 3 行，14 张里极罕见）。
  **实测覆盖全部 11 个可能位置**（杠组分别落在第 1~11 槽）：行数全是 2、每行槽位 `[7, 7]`、
  槽位合计 14、杠组不跨行、不越界、手牌卡高 129；两个杠组是 `4+3 / 4+3`、行 1 与行 2 各一个；
  打出一张后仍然 `[7, 7]`。
  **注意取舍**：为了让 4 格宽的整块永远落在一行内，杠组会被排到**行首**（不是它原本的排序位置）。
  想让它严格留在排序位置上，就只能接受 3 行、或者把牌缩小到一行放 10 格 —— 都不合适。
- **出牌区/杠区的牌本身就是 flex item，尺寸必须给像素**：写成 `--mj-w: 100%; --mj-h: 100%`
  是循环依赖，会被 flex 行**纵向拉满**（实测 26px 宽的牌被拉成 26×71 的竖条，截图里一目了然）。
  现在 `discardVars = { '--mj-w': 'var(--small-tile-w)', '--mj-h': 'var(--small-tile-h)' }`（**19×24px**），
  并且 `.discard-row { align-items: flex-start }`（默认 `stretch` 同样会拉长）。
  手牌那边相反：`.hand-tile` 是外层按钮（有 `width` + `aspect-ratio`），内层才用 `100%/100%` 填满。
- **手牌单张宽度用实测像素，不能用 `calc((100% - …) / 7)`**：杠组把 4 张包进一个 div 之后，
  里面的 `100%` 会按**杠组自身宽度**解析 → 那 4 张塌成 7px 宽的竖条（实测杠组 7×51）。
  现在 `measureHand()` 量一次卡片内宽（`ResizeObserver` 跟着变），把 `--hand-tile-w` 以 px 写回卡片。
- **牌面的尺寸变量是 `--mj-w` / `--mj-h`**（`MahjongTile` 的约定，不是 `--tile-w`）——
  写错了牌会变成默认尺寸（44×59），整块布局跟着错位。尺寸全局复用 `spriteVars()`，别自己算格子。
- **手牌显示顺序**：`displayItems` = 除「刚摸到的那张」（`drawnId`）之外按 `sortTiles` 排好，
  刚摸到的永远追加在最右；**打出一张后把 `drawnId` 清空**，于是整副手牌按顺序重排 —— 这就是
  用户要的「新牌先在最右、打出后按顺序进入手牌区」。
  **写测试时注意**：界面用的是排序后的顺序，**不能拿存档里 `hand` 的下标去点界面元素** ——
  两者顺序不同，按存档下标点会点到别的牌（我第一次验证就这么点错了，看着像「游戏打不胡」）。
  正确做法：先按 `data-tile` 读出界面顺序，再用 id 去存档里取牌面。
- **牌高度必须用 `aspect-ratio`，不能拿 `--hand-tile-w` 去算 `height`**：那个变量里含 `%`，
  出现在 `height: calc(...)` 里时 `%` 是按**父元素高度**解析的，实测整块手牌塌成 **21px**
  （牌面被压扁）。现在 `.hand-tile { width: var(--hand-tile-w); aspect-ratio: 131 / 168 }`，
  内层 `MahjongTile` 用 `--mj-w: 100%; --mj-h: 100%` 填满；飞牌是 `fixed`、没有可继承宽度，
  所以用出发牌**实测的像素宽**（`fly()` 里记 `w`）。

## 动画（摸牌 / 打牌）

两段动画共用一套机制：`flying`（`ref`）存 `{ tile, x, y, dx, dy, dur, scale }`，模板里渲染一个
**`position: fixed`** 的 `MahjongTile`，位置与位移通过 CSS 变量交给关键帧：

```scss
.flying { position: fixed; left: var(--x); top: var(--y); translate: -50% -50%;
          animation: solo-fly var(--dur) cubic-bezier(.3,.9,.4,1) forwards; }
@keyframes solo-fly { from { transform: translate(0,0) scale(1); }
                      to   { transform: translate(var(--dx), var(--dy)) scale(var(--scale)); } }
```

- `fixed` 定位：滚动时飞行轨迹不会跟着偏；`translate: -50% -50%` 是**独立属性**，不会和
  关键帧里的 `transform` 打架（`App.vue` 有一条全局 `button:active { transform }`，同理别用它居中）。
- 距离由 `centerOf(el)` 现算：打牌 = 手牌格 → 出牌区中心；摸牌 = **一张牌背** → **手牌最后一个格子**。
  **摸牌的起点必须量 `.tile-back`（一张牌背 ≈ 20px），不能量 `.wall-stack`**：整个堆是 200px 宽的
  容器，用它当起点会飞出一张巨大的牌 —— 用户报的「放大的效果」就是这个。飞牌尺寸取
  **出发元素实测的像素宽**（`fly()` 里记 `w`），缩放由关键帧平滑插值，不会有跳变。
- 动画期间 `busy = true`，手牌按钮 `:disabled`，避免连点把状态打乱。
- 动画结束后才提交数据（先飞、再删/加），最后一张牌落位后才判胡。
- **胡牌的收尾顺序**（用户要求）：① 先把 `drawnId` 清空 → 手牌**排整齐**（刚摸的那张归位）；
  ② 给手牌加 `.celebrate` 类，每张牌用 `--i` 做 `animation-delay: calc(var(--i) * 55ms)`
  **挨个跳一下**（14 张约 0.8s）；③ 跳完**才**置 `phase = won` + 撒花 + 浮层。
  实测：14 帧都能采到跳动、依次出现在 630→1801ms，浮层与烟花在 **1892ms** 才出现（跳完之后）。
- **动画时长**（用户要求「稍微慢一点」）：打牌 / 杠牌飞出 **380ms**、摸牌落位 **400ms**（原 280/300）。
  实测一次「打一张」里飞牌元素从 27ms 出现、776ms 结束 ≈ 380 + 400，肉眼能看清轨迹。
- **发牌波浪**（用户要求）：`dealRound()` 里把 `dealing` 打开 → 手牌（14 张，间隔 45ms）与牌堆
  （40 张，间隔 30ms）都用 `solo-deal` 关键帧（**从上方 12px 落下**、轻微过冲、落位）
  **从左往右依次入场**（延迟 `calc(var(--i) * …)`，两处都靠 `--i`）。总时长约 0.98s 后自动关掉。
  实测：手牌首张 109ms 亮、末张 701ms 亮（严格单调 ✓），牌堆同步（40 张时约 109→1270ms）。
  动画期间 `busy = true`（牌还没露出来也点不到），约 0.98s 后自动放开。
  ⚠️ 开关必须写在 `dealRound()` **末尾**：函数中部本来就有一句 `busy.value = false`，
  写在开头会被它立刻覆盖（第一版就是这样，实测动画期间按钮照样可点）。
  ⚠️ **入场方向必须朝上**：第一版写 `translateY(14px)`（从下方升起），波浪期间整页会**多出
  33px 可滚动高度**（`smoke.mjs` 的提示行直接报了出来）。向上位移不产生底部溢出，现在是
  `translateY(-12px)` 落位，实测波浪期间 `scrollY` 仍是 0。
- **摸牌/出牌都走同一个 FLIP**（用户要求「出牌区也要有动画」），落点精确：
  `flyToTile(tile, source, targetSelector, dur, commit)` 里
  **① 先 `hiddenTileId = tile.id` → ② 再 `commit()` 提交数据 → ③ `nextTick` 量到落点 → ④ 替身飞过去**。
  `fly()` 既接受元素也接受矩形；缩放由关键帧从「源宽」渐变到「目标宽」。
  实测出牌帧序列 `8,152 → 5,95 → 3,64 → 2,31 → 1,13 → 0,7 → 0,2 → 0,1`，**精确收敛到 0**。
  ⚠️ **① 必须在 ② 之前**：第一版是「先提交 → `nextTick` 两次 → 再藏」，中间会**露出 1~2 帧实体**，
  于是替身还在飞、手牌区那张已经亮着 —— 用户报的「有明显时间差、不像同一张牌」就是这个。
  先藏后提交，目标格子的**第一帧渲染出来就是隐形的**。
  ⚠️ **模板里的 `fly-hidden` 绑定必须和 CSS 规则成对出现**：手牌区那条 `visibility: hidden` 曾经漏写
  （出牌区一直有），于是**只有摸牌**会「替身在飞、实体还亮着」。
  实测修正前后逐帧对比：**「替身在飞却没有任何隐形实体」的帧 25 个 → 0 个**，
  飞行期间隐形实体数恒为 **1**；两段切换在同一帧内完成，不存在「替身 + 实体同时可见」的时刻。
  **验证时别只查类名在不在，要查 `getComputedStyle` 是否真的隐形** —— 我第一遍就是只查了类名。
- **恢复存档也播一次发牌波浪**（用户要求）：`onMounted` 里 `restored` 为真时调 `playDealWave()`。
  实测刷新后最小透明度 **0**、手牌首张 104ms 亮 / 末张 671ms 亮（左→右 ✓），牌堆同步。
  **烟花仍然只在真胡牌时放**（那条要求没变）。

## 存档（localStorage）

- `__solo__state`：`{ hand, wall, discards, kongs, omit, drawnId, phase }`（每张牌 `{ suit, value, id }`；
  `omit` = 本局缺的花色（`m`/`s`/`p`；现在**每局必有**，只有旧存档才可能为 `null`）—— **必须存**，否则中途刷新回来
  「本局没有X」那行就没了（实测左格变空）；
  `kongs` = `[{ suit, value, count: 4 }]`；
  `phase` = `play` / `won` / `lost`）。恢复时逐张校验花色与点数，不合法就当没有存档、重开一局。
- `__solo__streak`：当前连胜
- `__solo__best_streak`：最长连胜

**恢复在 `setup` 里就做**（`const restored = restoreState()`），首帧即最终样子。
**恢复要用到的 ref 必须都声明在 `restoreState()` 之前** —— 24 点分册里记过这个坑：
`answer` 声明晚了就是 TDZ，抛错被 `try/catch` 吞掉，表现为「退出重进永远恢复不了」。

⚠️ **这个坑本作又踩了一次**（`omitSuit` 声明在 `restoreState()` 后面）。而且它的现象**更隐蔽**：
`restoreState()` 开头就有一串 `return false` 的早退（没有存档 / 牌数不对就返回），
所以 **"没有存档时完全正常、只有带着存档重进才会炸"** —— 很容易误判成「恢复逻辑本身没问题」。
**识别特征**：把「首次进入」和「带着存档刷新」分开测；只测前者会一直测不出来。
自检办法：`restoreState` 里 catch 会 `console.warn`，带存档刷新时看控制台有没有这行。

### 坑：有杠的存档被当成坏档（用户报过）

`restoreState()` 的第一道校验原来写死 `s.hand.length !== HAND_SIZE`（14）。**杠出去的 4 张不再留在手里**，
有 1 个杠时手牌只有 11 张 —— 于是「杠完 / 杠完再打一张」的存档每次都被判坏档，退出重进直接开新局
（用户报的就是「有杠过牌的情况下，退出重进没有恢复、新开了一局」）。判据必须和 `isWin()` 一样按
**等效张数**算：

```
effective = hand.length + 3 × kongs.length   // 3 = MELD_SIZE
if (effective !== 14 && effective !== 13) return false;
```

13 是「刚打出 / 刚杠完、自动补摸还没落盘」的那一瞬间（`save()` 在 commit 时就写了）：恢复后由
`pendingDraw` 在发牌波浪结束后补摸一张；牌墙已空则直接 `lose()`。补摸前会再核对一次仍是
「等效 13 张」，防止玩家在波浪期间点了「新游戏」后把牌摸进新局。`kongs` 也要逐项校验牌面、
且同一种牌只能出现一次（不能杠两次）。

实测：种一份 11 张 + 1 个杠的存档 → 重进显示 11 张 / 杠行 1 组 / 牌墙原样，再打一张正常变成
「10 + 摸 1」；完整走一遍「杠 → 出牌 → 重进」也一致；另测 10 + 1 杠（补摸未落盘）恢复后自动摸成 11、
13 张无杠恢复后自动摸成 14、牌墙空时补摸落到失败局面、带杠的胜利局面直接恢复浮层。

**5 连点清记录（彩蛋）**：注册表里的 `recordsPrefix: '__solo__'` 只是为了让 `TopHeader`
**触发 emit**（它只删 `${prefix}${i}` 这种带数字的 key，删不到本作那几个 key），
真正的清理写在组件的 `onScoreReset()` 里（三个 key 全删 + 连胜 / 最长连胜清零 + 重开一局）。

## 结算层按钮：`nextRound`（下一局）

胡牌 / 摸完共用一个结算层（`.result`），里面只有一颗按钮：文案 `i18n('nextRound')`
（en `➡️ Next round` / cn `➡️ 下一局`），**样式是普通主色绿**（`game-icon`，不带 `replay-btn`），
点击行为仍是 `dealRound()`（保留连胜、按当前连胜给更难的档）。**别再给它加 `replay-btn`** ——
那是「重玩本关」专用的橙色描边样式（用户要求回到和闯关类一致的主色）。
