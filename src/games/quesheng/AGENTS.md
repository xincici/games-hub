# 雀圣（`src/games/quesheng/`）

> 这是根目录 [`AGENTS.md`](../../../AGENTS.md) 的**游戏分册**：只讲这个游戏自己的实现、
> 存档 key 和踩过的坑。**改这个游戏前先读这里**；跨游戏共用的约定看根目录。
>
> - 路由：`/#/quesheng`
> - i18n key 前缀：`__quesheng__`
> - 共享组件：`src/shared/`；牌面是一张裁好的**雪碧图**（`shared/mahjong-tiles.webp`，见下）

## 玩法

5×5 棋盘上随机铺 **14 张麻将牌**，这 14 张**一定是一副能赢的牌**（4 组顺子/刻子 + 1 个将）。
朝某个方向**滑动**，所有牌沿该方向移动直到碰边或被别的牌挡住（与 2048 同款、**不合并**）。
横排或竖排里**紧挨着**的牌若正好组成一组（三张：刻子或顺子）或一个将（两张对子），
就用高亮边框圈出来。点这一组的牌来消：**点齐三张消掉这一组、一对点满两张就消掉这一对**；
只有这两张是**相同的牌**、并且还能凑成刻子时，才浮出一个只提供「消除这一对」的提示气泡
（顺子点两张不弹提示，接着点第三张即可；气泡会主动避开第三张牌，见「界面」一节）。
一张牌同时属于多个可消组时，也是靠这样依次点来指定要消哪一组（点过的牌会亮起并抬起）。全部消完即过关。

判牌**与顺序无关**（和真麻将一致）：三张紧挨着的牌只要是「三张相同」或「同花色三张连续」
就算一组，不需要按点数排好序。

## 关卡曲线与标定

`board.js` 的 `levelConfig(level)`：

- **滑动步数上限：每关统一 30 步**（`MOVES_FLAT = 30`，用户要求把限制放宽；
  原来是第 1 关 14 步逐关收紧到第 20 关的 9 步）。步数用完还没消完就失败。
- **难度全交给摆盘**：`ease` 从 1 线性降到 0 = 开局**已经摆好的组数**从 4 组降到 0 组
  （第 1 关点掉摆好的组就行，第 19 关起全散着放）——也就是用户说的「前边的牌局简单一点、
  后边的难一点」。`MAX_LEVEL = 20`，之后重复第 20 关。

标定用的基础玩家：每一步把 4 个方向都试一遍，滑完只清「**清掉之后残局仍然拆得完**」的组，300 局/档：

| 已摆好的组 | 关卡 | 步数上限 | 通关率 | 用掉的步数 p50 / p80 / max |
| --- | --- | --- | --- | --- |
| 4 | 1 | 30 | 98% | 1 / 2 / 3 |
| 3 | 5 | 30 | 50% | 2 / 3 / 5 |
| 2 | 10 | 30 | 16% | 3 / 4 / 8 |
| 1 | 15 | 30 | 8% | 4 / 6 / 8 |
| 0 | 20 | 30 | 3% | 4 / 7 / 8 |

**注意：把步数上限从 14→9 放宽成统一 30 之后，这张表跟老表（91 / 46 / 17 / 10 / 3%）几乎一样** ——
因为基础玩家的瓶颈根本不是步数：它每步只看一层，经常滑到一个「没有任何可安全消除的组」的局面就卡死
（上表「用掉的步数」中位数只有 1~4，最多 8 步，30 步远没用到）。所以 30 步是**对人和求解器**的放宽：
上帝模式的求解器实测最多只用 8 步，现在完全不用省着走；而难度依旧由摆盘（4→0 组）承担。

这个基础玩家是**只顾眼前**的下界：它不会为了几步之后的局面留牌，人类玩家配合 undo/redo（以及
⚡ 上帝模式）会宽裕得多。

## 实现要点

- 纯逻辑在 `board.js`：`dealHand`（发一副能赢的牌，每种牌 ≤ 4 张）、`placeHand`（铺盘，
  `ease` 决定几组先摆成相邻）、`slide`（按方向压实、保持相对顺序、不合并）、`findGroups`
  （扫每行每列，找紧挨着的 2 张将与 3 张组）、`levelConfig`、`newGame`。
- **牌面是一张雪碧图**（`src/games/quesheng/tiles.webp`，917×840，**7 列 × 5 行**、每格 131×168，
  一张 181KB）。用户给了一张 9×4 的整副牌图，直接按格子裁下来、拼成雪碧图用 ——
  比 CSS 画省事得多，也自带那套立体牌风。
  - 裁法（跑过一次的 PIL 脚本）：格子 132.7×169.5，**每格再往里收 2px**（去掉相邻牌的边线），
    统一缩放到 131×168，**直接从原图拼成一张再存 webp**（只压一次，别拿裁好的 34 张再拼）。
  - **映射注意**：原图第 4 行的顺序是「北 白 南 中 發 東 西 北 白」，**不是**东南西北中發白，
    要按内容逐格对（最后一个白有知乎水印，弃用）。拼图顺序 = `SLOT_ORDER`
    （万 1-9 → 条 1-9 → 筒 1-9 → 東南西北中發白），格子下标 = `floor(i/7)`、`i%7`。
  - **取格子用百分比**：`background-size: COLS×ZOOM×100%, ROWS×ZOOM×100%` +
    `background-position: slotPos(c), slotPos(r)`，其中
    **`slotPos(i) = (k(i+0.5) − 0.5) / (n·k − 1)`**（`k` = ZOOM、`n` = 列/行数；`spriteVars()` 算好塞进 CSS 变量）——
    与元素实际尺寸无关，牌随视口缩放也不用改。实测跨行的 `m7`(列6) → `m8`(下一行列0)、
    末列 `p9` → 换行的 `z1`、以及最后一格 `z7` 都对得上。
  - **`ZOOM = 1.05`**：裁切时每格四周会带 1px 原图的列/行间隙，不放大的话牌贴着的那条边会出现
    **一条白线**（条牌最明显，用户报过）。放大 5% 等于把牌画小一点，把这圈边缘推出元素之外；
    两个轴同比放大，所以牌的长宽比不变。**定位公式别写错**：放大后不是 `c/(n·k−1)`，而是
    `(k(i+0.5) − 0.5)/(n·k − 1)`（让第 i 格的**中心**落在元素中心）。我第一版漏了分子里的 `k`，
    结果每张牌都露出半个邻居（截图一眼就能看出来）。
  - 牌的长宽比就是图片的 **1.282**（`metrics` 里的 `RATIO`），没有额外的底部厚度、
    也不需要给网格行高另留余量。
- **开局前先把雪碧图读进缓存**（`preloadTiles()` 来自共享模块 `shared/mahjongTiles.js`，
  和麻将英雄共用同一个 promise；`onMounted` 里 `await` 它再开局）。
  不预加载的话：牌元素按波浪淡入了、图却要等下载完才冒出来，**肉眼看到的顺序变成「谁先加载完谁先出现」**，
  完全看不出波浪（这正是用户报的「顺序不对」）。实测预加载后雪碧图 65ms 就绪、第一张牌 262ms 才出现。
- 动画三段：开局从左上到右下逐张铺开（延迟按 `r + c` 递增）、滑动用 `transform` 过渡、
  消除时先闪烁再消失。

## 上帝模式（求解器 + 演示）

**生成方式是关键**：`placeHand` 是「先把 `ease × 4` 组摆成相邻的三连，剩下随机撒到空格」——
随机撒点没有「滑动历史」可逆 ✗，所以「逆序操作」在这里用不上。而随机撒出来的局面在高关卡
**相当比例是步数上限内无解的**（实测第 20 关 300 局里 103 局如此），那种局玩家再厉害也过不去。

于是把「可解」这件事做进发牌里：`newGame` 现在**发到可解为止**（最多 40 次，`solvePuzzle` 一次
约 10ms，平均重发 1.5 次），并把解**缓存**在返回值里给上帝模式直接用（点下去零延迟开播）。
极端兜底：40 次都没发到就逐步放宽步数上限，宁可这关多几步也不给玩家一个解不开的局。
实测 5 档 × 300 局：**复演零失败**（每次滑动都是真滑动、每次消除都是当场的可消组、最后清空，
且用掉的滑动 ≤ 该关上限）；发牌耗时 p95 ≤ 71ms、max 158ms。

求解器 `solvePuzzle(board, movesLeft)`：
- 滑动算一步、消除不花步数，所以「先把能清的组清掉，再滑动」；
- **迭代加深**（先找步数最少的解，`m = 0..上限`）+ 记忆化「失败状态」（状态按每格的**种类**
  规范化 —— 同种类的牌彼此可换，可消组只看种类，不看 id）；
- **`canSplit` 剪枝**：剩下的牌必须还能拆成「若干组 + 至多一个将」，这是能不能赢的**必要条件**
  （滑动只换位置不改牌面）。加上它之后求解从「20 关 36% 失败、最慢 3.1s」降到「p95 ≤ 42ms」；
  拆牌**必须从最小的那张开始**（随便取第一张会在「最小张属于顺子」时误判，老坑）。

演示（`godPlay`）：只要**当前局面回到本关初始局**就可用，点下去按解逐步播。
判断条件是 `history.length === 0`（undo 栈里存的是每一步之前的快照，全部撤销回去 = 发牌时的那个局面；
快照连牌 id 都存了，所以缓存的最优解对同一副初始局仍然成立）。
**这里踩过一次**：第一版还额外要求 `future` 为空 —— 而玩家撤销回初始局时，`future` 里正留着
刚撤销掉的那些步骤，于是按钮一直是灰的（用户报的）。
- 滑动：真调 `applySlide(dir)`（0.17s 过渡）+ 停 `GOD_SLIDE_MS = 620ms`；
- 消除：先把 `selected` 设成这一组（牌抬起 + 橙色外框，让玩家看清消的是哪组）停 360ms，
  再 `clearGroup`（闪烁 520ms）+ 停 600ms；
- 播放中再点一下按钮 = 停止（`stopGod()` 立刻唤醒所有等待），换关 / 卸载也会停。
- **播放期间彻底不接受输入**：`.automask` 盖在牌上面（实测 `elementFromPoint` 打到的是它、
  强行滑一次步数保持不变），`onTileClick` / `onBoardDown` / `onPointerUp` 里也都判 `godPlaying`。

**一个值得记的样式层级坑**：`.automask` 一开始被我跟着 `.opt-area` 一起嵌套（因为替换的是
`.opt-area` 里那行说明文案），编译成 `.opt-area .automask` —— 而它实际渲染在 `.board` 里，
**根本匹配不上**。表现有两个：① 它变成 grid 里的普通子项、多撑出一行，把棋盘从 450 撑到 538
（5 行变 6 行，`document.scrollHeight` 也跟着涨）；② 它没有任何定位，**完全挡不住输入**。
修法是把 `.automask` 的样式挪到 `.game-area` 同级（`position: absolute; inset: 0; z-index: 5`），
棋盘尺寸随即恢复（实测平时/播放中都是 360×450，320 下 210×260）。

实测（390 宽）：第 1 / 5 / 12 关都能从 14 张自动打到 `result win`，用时 7.0 / 7.4 / 7.6s，
用掉的滑动 2 / 2 / 3 步（都在上限内），期间遮罩层在、结束后撤掉、按钮回到「⚡ 上帝模式」并禁用。

可用性的四次实测（第 5 关，步数上限 30）：初始局**可用** → 手动滑一步后**禁用**（撤销可用、步数 30→29）
→ **撤销回初始局后恢复可用**（此时撤销禁用、重做可用，正是 `future` 非空的情形）→ 点上帝模式
一路打到 `result win`（14 张清空、用掉 2 步）。

## 坑

1. **`dealHand` 检查「每种牌不超过 4 张」时要按「这组牌每种各需要几张」算**：第一版对刻子也
   只按 +1 计，于是 3 张同牌还能再加一组刻子 → 一局里能出现 6 张同牌（实测出现过）。
   现在用 `meldNeed(group)` 统计每种的需要张数再比。
2. **`placeHand` 的「预摆好的组」必须从手上的牌里挑一个真正成立的组**：第一版先把 14 张
   shuffle 再取前 3 张摆成相邻 → 摆出来的根本不是顺子/刻子，第 1 关一点都不简单（贪心通关率 2%）。
   现在用 `takeMeld()` 从剩余牌里挑一个真成立的组再摆。
3. **写标定脚本时：拆牌必须从「最小的那张」开始**。顺序无关的拆牌若随便取第一张，
   会在「最小张属于顺子」时误判为拆不开（实测 500 副合法手牌被误判 54 副）。
4. **清组不能只看当前能不能成组，还要看「清完剩下的牌还能不能拆完」**：这是本作最容易踩的设计坑 ——
   随便清一组会把残局变成永远拆不完的死局（实测只顾眼前的贪心在最高难度通关率 1%，
   加上残局检查后才 3%，而人类用 undo/redo 可以回退重来）。**这也是 undo/redo 存在的意义**。

## 界面

- 统计条三格：「🏁 关卡 / 🀄 剩余 / 👣 步数」，底部有本关进度条（已消张数 / 14）。
- 操作区两半：「🎮 新游戏」（左，点开共用的 `ConfirmDialog`：取消 / 重玩本关 / 确定重来）与
  **⚡ 上帝模式**（右）。原来左边那句「滑动合并 · 点组消除」的说明文案已按用户要求去掉，
  两个按钮的位置也按用户要求互换过一次（**现在是新游戏在左、上帝模式在右**）。
- 上帝模式播放期间**没有任何底部步骤文案**（用户要求「仅演示操作即可」）：下方仍是正常的撤销卡，
  只是两个按钮都禁用（`!canUndo || godPlaying`）；棋盘上盖一层透明 `.automask` 挡住点击与滑动
  （与点击游戏同款做法），JS 侧 `onBoardDown` / `onPointerUp` 里也各加了一道 `godPlaying` 判断兜底。
- **撤销 / 重做放在游戏区下方**，抄点击游戏那张 `.card.undo-card`：两个 `.undo-item` 各一个按钮
  （`i-carbon-undo` / `i-carbon-redo` + 文字，中间一条竖分隔线），不可用时 50% 透明 + `not-allowed`。
  一开始我把它挂在顶栏插槽里，用户要求改到游戏区下方并保留「新游戏」。
- 顶栏插槽留空（没有模式开关）。
- 分组高亮是**一个圈住整组的圆角框**（`.group-ring`，绝对定位、`pointer-events: none`），
  不是给每张牌描边；点选中的牌自己抬起 3px 并套一圈主色 `outline`。
  **只画真正该圈的那个框**：三张相邻的刻子会同时产生 [0,1]、[1,2] 两个「对子组」，
  再各画一个框就成了「一个大框套两个小框」。`ringGroups` 会把**已经含在三张组里的对子框滤掉**
  （用户要求），实测刻子从 3 个框变 1 个 `210×88`、孤立一对仍是自己的 `140×88`、顺子不受影响。
  **注意只过滤显示** —— `groups` 里仍然保留对子组，因为歧义提示里的「消除这一对」要靠它。
  **框的颜色是浅橙 `--group-ring: #ffa63d`**（用户指定），和主色绿区分开：绿＝可操作、橙＝这一组能消；
  它不跟主题变量走，因为深浅两套主题下都够醒目。
- **消除规则**（`onTileClick` 里三段）：
  - 点齐**三张**且正好是一个三张组 → 直接消；
  - 点满**两张**且这两张**只**构成一对（不属于任何三张组）→ **直接消一对**，不弹提示；
  - 点满两张、它们是**相同的牌**且同时还能凑成刻子（歧义，例如「中中中」的前两张）→ 不自动消，
    浮出提示气泡（`clear-tip`），里面**只给一条路**：可点的「✨ 消除这一对」。
  - **顺子（三张连续）点两张不弹任何提示**（用户要求）——没有对子可消，直接接着点第三张即可；
    提示也因此不再出现「或再点第三张」这句（i18n 的 `clearMeldHint` 已删除）。
  （交互演进：先要求「一对要点提示确认」→ 改成「只有一对相邻时点两张直接消」→
  再改成现在这样：提示只在「点满的两张是相同牌、且还能凑成刻子」时出现。）
- **提示气泡的位置要避开第三张牌**（用户要求，避免误点）：`hint` 里算出第三张牌（同一个三张组里
  没被点中的那些格子）相对这两张牌包围盒的方向，然后
  - 纵向：第三张在正上方 → 气泡改挂**下方**（`--tip-ty: 0%`，箭头翻到顶部朝上）；
  - 横向：第三张在右边 → 气泡向左延伸（`--tip-tx: -100%`）、在左边 → 向右延伸（`0%`），
    都没有就居中（`-50%`）。**这一步是必要的**：气泡宽约 96px，320px 屏上两张牌只有约 72px，
    居中时会向旁边溢出压到第三张。
  - 坑：`qs-tip-in` 关键帧里**必须沿用 `--tip-tx / --tip-ty`**，不能像原来那样写死
    `translate(-50%, -100%)` —— 否则入场动画期间气泡会被拽回上方（动画的 transform 优先级更高），
    动画结束再「啪」地跳下来。
  实测 5 种盘面 × 390/320 两档共 10 例：顺子不弹提示、刻子只显示「✨ 消除这一对」、
  既不压第三张也不压已选的两张、都在视口内（入场动画中途也不越位）。
- 帮助文案（`help2` / `help3`）跟着这条交互一起改过，别再写成「点任意一张即可整组消掉」。

## 布局与动画的四个坑

1. **绝对定位的牌要加上棋盘自己的 `padding` 偏移**。棋盘的包含块是 **padding box**，
   `.tile { top: 0 }` 落在 padding **外沿**，而网格里的 `.grid-cell` 是从内容盒（= padding 之内）开始排的，
   实测整盘牌往左上偏了 8px（牌与格上下留白 `-8/8`）。`posOf` / `ringStyle` 里都要补 `metrics.pad`。
2. **网格行高必须按牌高走**：牌是竖牌（图片比例 1.282），`grid-auto-rows` 若还按格宽算，
   每行都会被下一行压住、牌面下半截被切掉（和猎手候选区、Emoji 大师是同一个坑）。
   之前用 CSS 画时还多一条「格高要按牌面 + 底部厚度算（1.425）」，换成图片后长度就是
   图片自己的比例（`RATIO = 1.282`），厚度已画在图里。
3. **`.group-ring` 一定要 `box-sizing: border-box`**：2px 边框画在 content-box 之外，框会比牌大 4px
   （实测四边 3,3,7,7 → 修好后 3,3,3,3）。
4. **滑动的纵向步长 ≠ 横向步长**（`stepY = cellH + gap`、`stepX = cell + gap`），牌的 `left/top` 过渡
   与分组框的尺寸都得用各自那一个，别混用。

三段动画：

- **铺牌**：`animation-delay = (行 + 列) × 60ms`，波前从左上角一路扫到右下角（实测跨度 ~484ms）。
  三个注意点：① 每次开局 `dealSeq += 1` 并把它拼进 `:key` —— 否则 `newGame()` 里 `resetUid()`
  让牌 id 从 1 重来、key 撞上，Vue 会复用元素、**入场动画不重播**；② 恢复存档也走同一段铺牌；
  ③ **铺牌期间 `groups` 置空**，高亮框必须等牌全部出现之后再算（用户明确要求；实测首个高亮框
  896ms 出现，晚于牌全部出现完的 ~620ms）。
- **滑动**：`left/top` 的 0.17s 过渡（纵向步长与横向不同）。
- **消除**：`qs-blink`（闪两下再缩掉，520ms 后从数据里移除），见下。

## 已知情况

- **320×568 下整页会纵向滚动约 10px**（换成图片牌面后从 30px 降到 10px）：5×5 的竖牌本身占地方，
  高度预算（`innerHeight − 262 − 下方撤销卡 66 − 内边距与缝隙`）算出来的格宽会触到 34px 下限
  （再小牌面就看不清了），最小屏上收不进一屏 —— 与 Emoji 大师在 320×568 下滚动 46px 属同类情况。
  实测 390×844 / 375×667 都是 0px，只有 320×568 差一点点。

## 消除的闪烁动画（踩过）

`clearGroup()` 会把格子置 `null`，牌**立刻就不在 `tiles` 里了** —— 第一版只给 `tiles` 里的牌挂
`:class="{ clearing: clearing.has(t.id) }"`，于是这个类**永远挂不上**，表现是牌「啪」地瞬间消失、
完全没有 `qs-blink`。修法是照麻将英雄那样**单独渲染一层浮影**：

```
const clearingTiles = computed(() => [...clearing.value.values()]);   // 存的是 { ...tile, cell }
<span v-for="t in clearingTiles" :key="`clear-${t.id}`" class="tile clearing" :style="posOf(t.cell)">
```

（`clearing` 这个 Map 里一定要带 `cell`，否则浮影层不知道该摆回哪一格。）
实测修好后浮影层的 opacity 是 `0.96 → 0.15 → 0.98 → 0.15 → 0.01`，
即「暗→亮→暗→淡出」两下闪烁，与扑克炼金术 / 麻将英雄一致。
