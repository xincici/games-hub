# 24 点（`src/games/point24/`）

> 这是根目录 [`AGENTS.md`](../../../AGENTS.md) 的**游戏分册**：只讲这个游戏自己的实现、
> 存档 key 和踩过的坑。**改这个游戏前先读这里**；跨游戏共用的约定看
> [`docs/CONVENTIONS.md`](../../../docs/CONVENTIONS.md)。
>
> - 路由：`/#/point24`
> - i18n key 前缀：`__point24__`
> - 共享组件：`TopHeader` / `confetti`；`board.js` **不 import 任何东西**（见下，为了能离线验证）
> - 单局制（没有难度分档），记录是**当前连胜 / 最长连胜**；难度按关卡递增

> 玩法简介（面向玩家）见同目录的 [`README.md`](README.md)；本文档只讲实现、存档与踩过的坑。

## 玩法要点

4 个 1~9 的数字（可重复），**一定凑得出 24**；把 4 个数字各用一次，用 `+ - × ÷` 与括号组成
结果等于 24 的算式即过关。点数字 / 符号 / 括号往算式里加，「⌫ 退格」撤回。查看答案 = 放弃
（当前连胜清零，最长连胜保留）。界面上「用过的数字」「当前不能加的符号」都要置灰。

## 实现

- **`board.js` 是纯逻辑且不 import 任何东西** —— 这点是**故意**的：可以直接用 node 跑离线自检
  （`node -e "import('./src/games/point24/board.js')"`），把「发出来的题一定有解、答案串能被独立
  解析回 24、难度确实递增」这几件事在**不开浏览器**的情况下断言掉。整个功能就是靠它抓到下面那个
  渲染 bug 的。
- **全程精确分数**（`{n, d}`）而不是浮点。`3 3 8 8` 这类题的解是 `8 ÷ (3 - 8 ÷ 3)`，中间会出现
  8/3；浮点下会差一点点，把可解的题判成无解（或反过来）。`solveAll()` 枚举所有解（挑两张合并、
  递归），`evalTokens()` 用递归下降对玩家拼的 token 求值，两者共用同一套分数运算。
- **难度是启发式分档**（`hardness()` → 0~4，单道题的度量）：解越多越易（≥20 解 = 0 档，≤2 解 = 3 档），
  若**所有**解都必须经过分数再 +1。
- **关卡曲线是「趋势向上」而不是逐关递增**（用户明确要求：「难度不一定一直增加，有上升的趋势即可」）：
  `targetHardness(level, rand)` 先算一条连续水平线 `(level-1)/4`，再在它附近随机取整
  （30% 更简单、15% 更难、其余贴着水平线），**第 1 关固定 0 档**。
  `newPuzzle()` 按这个档位拒绝采样，**同时卡上界**（`h > need` 也丢掉，前 300 次严格、之后放宽一档，
  最后还有 200 次「只要有解」的兜底 + 固定牌组）。
  **上界是必须的**：原来只有下界（`h >= need`），于是 `need = 0` 的第 1 关照样会发出 4 档的难题 ——
  用户报的「点新游戏不是从简单的题开始」就是这个。
  实测（每关 80 题）：关卡 1 平均难度 **0**、平均评分 **31~34**（区间 8–51），
  最难的关卡平均 **82~89**；单看一局 1→15 关的评分序列（一次实测）
  `30 35 56 48 48 18 51 43 43 51 100 51 85 67 96` —— **有上升趋势，也有明显起伏**。
  生成耗时 0.4ms（简单档）~ 25ms（最难档，拒绝采样多）。
  （每关的数字会随随机小幅波动，别把它当成固定曲线。）
- **「新游戏」= 从头开始，**当前连胜 > 0 时**先二次确认**（用户要求；连胜本来就是 0 时没什么可清，
  直接开新局、不打扰）。确认时点按钮只弹确认：
  确认文案是「开启新游戏会清除当前连胜并重新开始，确认吗？」（i18n 的 `newGameConfirm`），
  按钮是「取消 / 确认」（共用 `ConfirmDialog` + `show-replay=false` 去掉「重玩本关」）。
  确认后 **当前连胜清零**、`level` 回到 1、发一道第 1 关的题；**最长连胜作为记录保留**。
  想保留连胜接着往上走，用胜利浮层的「下一关」（那里才 `level + 1`）。
- **token 规则在 `appendable(tokens, tok)` 里**（界面直接拿它判 `:disabled`）：数字只在「该出现值」
  时加且不能重复用；运算符只在值之后加；左括号只在「该出现值」时加、最多 3 层；右括号只在值之后
  加、且必须还有未闭合的左括号。
- 判定：4 个数字全部用上 **且** 语法完整（括号配平、以值结尾）时才算一次完整算式 —— 等于 24 即
  `win()`，否则显示「还不是 24 · = N」（`evalTokens` 给的分数字符串）。**只在这两个条件都满足时
  才提示**（见「布局与界面」）。
- 胜利：`phase = won` + `confetti()` + 当前连胜 +1（并刷新最长连胜）+ 浮层（盖在算式 / 数字 / 符号
  这三块上，`.game-area` 是定位上下文）。「下一关」= 关卡 +1 发新牌；「新游戏」在上一局赢了时也进
  下一关、否则本关换一道题。

## 布局与界面

五块从上到下（用户指定顺序）：分数区 → 按钮区 → 算式区 → 数字区 → 符号区，都在 `.wrapper` 里，
数字区与符号区嵌在 `.game-area`（胜利浮层的定位上下文）。实测各块高 **88 / 72 / 104 / 72 / 60**
（375×667；操作区改成下坠那套之后高度是 72 = `var(--row-height)`），内容总高 **548**；
三档视口（375×667 / 390×844 / 320×568）纵向与横向溢出都是 **0**（320 下 548 < 568，刚好放得下）。
符号按钮用 `flex: 1` 平分一行（6 个：`+ − × ÷ ( )`）；数字按钮固定 56×56。
界面上显示 `−`（U+2212），内部一律 ASCII `-`，见「坑」第 3 条。

几处按用户要求定下来的细节，改之前先看一眼：

- **分数区只有两格：「🏆 最长连胜 / 🔥 当前连胜」**。**关卡不再展示**（用户要求去掉 —— 这个字段没什么用），
  但它内部仍然存在：它是难度的唯一来源（见「难度是启发式分档」），也仍然写进存档。
- **「💡 查看答案」按钮（英文是 `💡 Answer`）是可点击时橙色**（`.answer-btn:not(:disabled) { background-color: var(--god-bg) }`，
  与上帝模式同一个橙 `#c2410c`，白字 5.18:1）—— 它等于「放弃」，和绿色的「新游戏」区分开。
- **退格是算式区最右侧的小按钮**：`.undo-mini`，30×30，`position: absolute; right: 8px; top: calc(50% - 15px)`
  （**在卡片里垂直居中**，且这个居中不依赖 `transform`，见下）；**不在按钮区**；
  算式本身用 `padding: 0 34px` 给它让位，否则长算式会被它压住。
  **位置绝不能用 `transform: translateY(-50%)` 居中**：`App.vue` 有一条全局规则
  `#app button:not(:disabled):active { transform: … }`，按下的瞬间会把你的 transform 顶掉，
  按钮先下移再归位 —— 用户报的「点退格时按钮向下闪一下」就是这个（见根 PITFALLS）。
  算式卡片**高度固定 104px**（`.expr` 用 `flex: 1` + `overflow-y: auto`），这样 token 从一行变两行时
  卡片不长高，退格与下方那行小字都不会跟着跳。
- **「还不是 24 · = N」只在「4 个数字都用完 + 算式完整 + 结果不是 24」时出现**。
  数字没用完或算式还没拼完时**一律不提示**（用户明确要求：别在玩家还在拼的时候催）。
  **这行提示是绝对定位钉在卡片底部**（`position: absolute; left/right: 12px; bottom: 4px`）：
  它原来在普通流里，一出现就把 `flex: 1` 的算式压小、整行 token 跟着上移 ——
  用户报的「文字出现的时候算式的位置不要变」就是这个。实测提示出现前后
  `.expr` 的 `top` 268 / 高 80、首个 token 的 `top` 294 **完全不变**。
- **点查看答案直接在算式区摆出答案算式**（渲染成同一套 token，**不写「参考答案」这类前缀**），
  答案下方居中一行小字「查看答案，连胜中止」（i18n 的 `gaveUpNote`）。
  **放弃之后数字与符号一律禁用**：`:disabled` 除了 `!appendable(...)` 还要带上 `phase !== PLAY` ——
  只判 `appendable` 的话，放弃时 token 还是玩家原来那些、按钮看起来照样能点（`add()` 里虽然有
  `phase !== PLAY` 的早退，点了什么都不会发生，但界面必须看得出来不能点）。

## 难度评分（1~100）

操作区**照 Emoji 下坠那套写**：`card.opt-area` = `opt-half（评分，flex 3）` + `divider` +
`start-wrapper（新游戏，flex 3.5）` + `divider` + `start-wrapper（查看答案，flex 3.5）`，
最左侧那格里是 `score-cell`，**一行**显示「题目评分 · 80」/「Score · 80」（标签走 i18n、中间的「·」在模板里），
两侧各一条 `.divider`。两个 span 字号不同（12 / 16），所以用 **`align-items: center` + 两边都 `line-height: 1`**
让视觉中心重合（实测中心差 0；用 `baseline` 时标签 `line-height: normal` 与数值 `1.1` 不一致，看着就是没对齐）。
**按钮不写 `flex`，取自然宽度、在格里居中** —— 第一版写成 `flex: 1` 撑满整格，用户反馈「太长」；
下坠就是自然宽度的写法（实测按钮宽从撑满格的 129px 收到 **79 / 92px**，所在格 119px）。
评分由 `scorePuzzle(nums, sols)` 纯函数算出来（`newPuzzle` 顺手带上 `score`；**存档里不存**，
恢复时按数字重算 —— 和答案一样）。

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 基础分 | 30 | |
| 解的个数 | 0~40（解越多越低） | 不同**算式**的个数 |
| 必须用分数 | 0 / 8 / 20 | 所有解都要经过非整数最烦人 |
| 每个解都要除法 | 0 / 12 | 有一条不用除法就不加 |
| 数字互不相同 | +8 / +3 / −6 / −14 | 四个都一样最省事 |
| 纯加减就能成 | −25 | 一眼看穿 |
| 只有一次乘除 | −8 | 也很直白 |
| 数字里有 1 | −8 | ×1 / ÷1 的凑法太多 |

实测：`3 3 8 8`（唯一解 + 必须分数 + 必须除法）**96**、`6 6 6 6`（纯加减即可 + 四个一样）**9**；
560 道随机题的区间是 **2~100**、平均 64；逐关平均 43 → 98（第 10 关起明显变难）。
`scripts/check-point24.mjs` 会断言区间、极端值与「逐关递增」，并核对 `score` 与重算结果一致。

**坑：别只把「纯加减」扣 10 分。** 第一版就是这样，于是 `6 6 6 6` 拿到 **40** 分 ——
因为 `solveAll` 按**算式串**去重，四个相同数字会把排列全部折叠成少数几个算式，
看起来"解很少"＝像难题，其实一眼就会。**「易」的信号必须由减分项主导**，
不能指望「解的个数」单独把简单题压下去。

## 不生成无解的题（三道保证）

1. **生成侧**：`newPuzzle()` 只接受 `solveAll(nums).length > 0` 的牌组；按难度拒绝采样 600 次挑不到
   就放宽一档；最后还有 200 次「只要有解」的兜底，再不行直接用固定牌组 `FALLBACK_NUMS = [6,6,6,6]`
   （6×6−6−6=24）—— **不可能发出无解的题，也不可能死循环**。
2. **恢复侧**：`restoreState()` 校验数字形状之后**还会再解一次**，无解就丢掉这份存档重发。
   （存档被手改坏 / 版本残留时，不能把一道死题摆给玩家。）
3. **答案侧**：存档里**不存答案**，恢复时用 `solveAll(nums)[0].expr` 重算 —— 否则重进后点
   「查看答案」会什么都没有（这是实测发现的坑）。同理，发牌时就先算好答案，点按钮零延迟。

用 `node scripts/check-point24.mjs [每关样本数]` 随时复验（纯逻辑、不开浏览器）：它断言每道题有解、
答案串能被**独立解析**回 24、数字都在 1~9、难度随关卡递增，并给出逐关的难度 / 解数 / 最慢耗时。
默认每关 200 题；实测近 2000 题 **0 道无解、0 条答案复算失败**。
（浏览器侧另测过：连开 30 局逐局用求解器确认可解、**0 局无解**；往存档里种一道无解的坏牌
`1 1 1 1` 后重进，页面会丢弃它并重发一道可解的。）

## 存档（localStorage）

- `__point24__state`：`{ level, nums, tokens, phase, revealed, note }`（`phase` = `play` / `won` / `gaveup`；
  恢复时校验 `nums` 是 4 个 1~9 的整数，不符就当没有存档、重开）
- `__point24__streak`：当前连胜
- `__point24__best_streak`：最长连胜

**恢复在 `setup` 里就做**（`const restored = restoreState()`），这样首帧就是最终样子，不会先画一个
空算式再补状态（这是本项目反复踩的坑，见根 AGENTS）。**恢复时什么都不播**：胜利局面重进只把
遮罩摆出来，**不放烟花**（用户明确要求；也是根 AGENTS 的老约定）。烟花只在真正打赢的那一刻放
（`win()` 里直接 `confetti()`）。

**坑：`restoreState()` 用到的 ref 必须都声明在它前面。** 它内部要给 `answer.value` 赋值，
而我一度把 `const answer = ref('')` 放在它**后面**（发牌那一节里）—— 那就是 TDZ，抛 `ReferenceError`，
又正好被 `try/catch` 吞掉，于是 `restoreState()` **永远返回 false**：现象是「玩了两步退出重进，
局面没了、每次都在重发新题」。实测证据链：玩两步后存档里 `nums/tokens` 都是对的，
离开再回来却变成另一组数字。**现在 `catch` 里会 `console.warn`**，不再静默。
（同一个 `setup` 里凡是恢复路径要用的状态，一律先声明再用。）

**5 连点清记录（彩蛋）**：`TopHeader` 只会删 `${recordsPrefix}${i}` 这类带数字的 key，
而本作的两个 key 是不带数字的 —— 所以注册表里给 `recordsPrefix: '__point24__'`（仅仅为了让它
**触发 emit**），真正的清理写在组件的 `onScoreReset()` 里（删两个 key + 清零内存状态 + 重开第 1 关）。
顺带一提：贪吃蛇 / 2048 这类没写 `recordsPrefix` 的条目，5 连点其实**什么都不会发生**。

## 坑

1. **渲染表达式时，「要不要加括号」要看父节点的运算符，不是自己的**。
   第一版写的是 `isRight && (node.op === '-' || node.op === '÷')` —— 看的是**自己**的运算符，
   于是 `6 × (9 − (4 + 1))`（= 24）被渲染成 `6 × (9 - 4 + 1)`（= 36）。
   因为按表达式串去重，这个**错的串**还可能把真正等于 24 的解挤掉。
   正确规则：`-` / `÷` 的**右**孩子只要同优先级就必须加括号。
   **是离线自检抓到的** —— 拿渲染出来的答案串重新解析求值，28 个断言当场失败（`=36`、`=32`…）。
   教训与根 AGENTS 里那条一致：**换一条独立的路径复算产物**，别只信生成侧的自证。
2. **浮点会毁掉这个游戏**：`3 3 8 8` 这种题必须用分数；用 `Number` 算会把 `8/3` 的舍入误差带进
   比较，`=== 24` 永远不成立。全程 `{n, d}` 并约分，比较写成 `f.n === 24 * f.d`。
3. **`−`（U+2212）与 `-`（ASCII）不是一回事**：界面上显示的是排版更好看的 `−`，内部运算一律用
   ASCII 的 `-`（`tokOf()` 里转换）。混用会让 `PREC[op]` 取到 `undefined`。
4. **按钮宽度**：操作区照下坠写「自然宽度居中」，375 下实测 **79 / 92px**（撑满格会是 129px，用户嫌长）；
   ⌫ 用图标不写文字（文案放进 `title`）—— 三件东西挤一行时它就是这么处理的。
5. **64px 首行间距要写 `.wrapper` 的 `padding-top`，不能写 `.score-area` 的 `margin-top`**：
   顶栏是 `fixed`（不在流内），于是 `.score-area` 是这个页面**第一个在流内的元素**，它的 `margin-top`
   会塌陷出 `#app`，而 `#app` 有 `min-height: 100dvh` —— 整页恒多出 64px 可滚动。
   实测内容总高只有 **480**（视口 667），`scrollY` 却也是 **64**；改成 padding 后 375/390/320 全是 0。
   **判据要先量「内容总高 vs 视口」**：总高没超却仍能滚，就是塌陷（Emoji 镜像踩的是同一个坑）。
